# NEW — "Briefing" Tab (dashboard summary/report page)

**Status:** BRAINSTORM — not yet spec'd in detail, not implemented.
**Created:** 2026-08-24 (Claude, via Filesystem MCP, brainstorm session with Ahmet)

---

## 1. What this is

A new dashboard tab that acts as a single "start here" page: a rolled-up,
LLM-narrated summary of system health + trade ideas, with click-through links
into the existing detailed tabs. Two purposes that must stay visually and
architecturally separate even though they live on one page:

- **Operational digest** — is the pipeline healthy, what's broken, what
  ML/Gate thresholds passed or failed, data freshness.
- **Decision-support report** — what to trade: must-check tickers, combo
  ideas (long/short groupings), risk/reward tiers, "gamble" tier.

Mixing these into one LLM prompt/summary risks burying health warnings under
trade ideas (or vice versa) — keep them as two distinct sections/prompts even
if generated by the same job.

## 2. Naming

Home page already owns "OVERVIEW". Proposed nav label: **`📋 BRIEFING`**
(fits the Control Tower / aviation branding — a tower briefs pilots before
they fly). Route: `/briefing`. Placed in nav right after `⭐ HIGHLIGHTED`.

Alternatives considered: Digest, Mission Control, Cockpit, SITREP — Briefing
reads clearest and matches existing branding tone without being overly
militaristic.

## 3. Page layout (three zones, top to bottom)

1. **Status strip** — reuse existing `.kpi-strip` / `.kpi` components.
   Pipeline health, last run timestamp, ticker coverage (e.g. 126/135), Gate
   2/3/4 status, open alert count. One glance = is anything broken.
2. **LLM narrative panel** — on-prem-generated plain-English summary in its
   own `.panel`, visually separated from raw data below. Model-picker
   dropdown in the panel header (Ahmet has several local LLMs — pick which
   one generated this). Shows an "as of" timestamp, not live-generated per
   page load (see §6).
3. **Click-through sections below** — each is its own `.panel` reusing
   existing styles (`.pick-card` from highlighted.html, `.tbl` from other
   tabs) with a "View full →" link into the source tab. Do not duplicate
   full detail here — this page is a jumping-off point, not a replacement
   for the existing tabs.

## 5. Shorting / leverage — explicit caution

Per existing project principle (see hedge-fund-quant-engine skill): short
selling has two separate tracks — (a) current informational inverse-ETF
advisory panel, (b) future full IBKR live-execution migration. The Briefing
page's combo-trade and leverage sections must visibly label themselves as
**advisory only**, and must not imply direct execution capability that
doesn't exist yet. Do not let this page become the place where that
separation quietly blurs.

## 6. On-prem LLM integration

- Ahmet has several local LLM options — page should have a picker, not a
  hardcoded single model.
- Narrative generation should be tied to pipeline run completion (or a
  scheduled job), not regenerated on every page load — cheaper, and gives a
  meaningful "as of" timestamp instead of a summary that subtly changes on
  every refresh.
- Two separate prompts/summaries (operational digest vs. decision-support),
  not one blended prompt — see §1.
- Output should be stored (new table or reuse `pipeline_logs`-style pattern)
  so the page can render instantly instead of waiting on LLM inference at
  request time.

## 7. Open questions to resolve before writing a full spec

1. One unified `checks`/`threshold` table across ML gates, risk limits, data
   quality, reconciliation — or keep separate tables and join at read time?
2. Combo-trade construction: real correlation/beta-neutral pairing logic, or
   a simpler "long book / short book side by side, you eyeball the balance"
   v1?
3. Does "leverage" mean anything concrete yet (does the Trade Republic
   account actually support margin), or is this pure what-if advisory for
   now?
4. Where does the on-prem LLM run relative to the Flask app — same machine,
   called via local HTTP, or a separate scheduled job that writes results to
   the DB for the app to read?
5. "Stay away" tickers — worth a real rule set, or leave as an inferred/soft
   signal for v1?

## 8. Suggested build order

1. Rollup query layer (operational digest half only — no LLM yet). Cheapest,
   highest immediate value, reuses existing tables entirely.
2. `/briefing` route + template, status strip + click-through sections
   (still no LLM narrative — just the aggregated data, styled to match).
3. On-prem LLM narrative panel wired to the operational digest.
4. Must-check / risk-reward / gamble-tier sections (decision-support half),
   reusing `highlighted.html`'s data source.
5. On-prem LLM narrative for decision-support half (separate prompt).
6. Combo-trade construction (new logic, correlation-checked).
7. Leverage section — only after open question #3 is answered.
