# Portfolio Risk Intelligence: Implementation Plan

This document serves as the prioritized plan for enhancing the portfolio's risk management capabilities. It has been audited against the current live codebase, filtering out already-implemented features to focus entirely on what is missing and valuable.

## 1. Current Live Risk Stack (Do Not Re-implement)
The following components are already live and functioning in the system:
- **Monte Carlo VaR**: Server-side 10,000-path lognormal MC simulations run in `/api/ticker_mc` and `/api/portfolio_mc`.
- **Stress Scenarios**: Historical EUR loss calculations are active in `/api/stress_tests` and are beta-adjusted.
- **Data Integrity Validation**: `engine/data/validation.py` already handles price spikes and zero-price filtering.
- **Regime Integration**: Wired into the BL and feature store (e.g., `transition_warning`, `macro_ew_count`).
- **Data Freshness Guard**: Active in `health.html` and `/api/freshness`.
- **EUR Normalization**: All prices in the DB are correctly stored and calculated in EUR.

---

## 2. High-Priority Implementation Roadmap

### Priority 1: Ensemble Monte Carlo VaR (`engine/risk/monte_carlo.py`)
The current MC VaR uses a single Gaussian assumption. We must build an ensemble model:
- **Student-t Model**: Captures equity tail risks that Gaussian systematically underestimates.
- **GARCH-Filtered Model**: Makes VaR reactive to current volatility clustering rather than relying solely on 252-day trailing vol.
- *Implementation*: Use Cholesky decomposition to correlate returns. Combine Gaussian, Student-t, and GARCH outputs.

### Priority 2: Kupiec POF Backtest (VaR Health Check)
A script to perform Kupiec's Proportion of Failures Test.
- **Logic**: If historical 95% VaR is breached >12 times in 252 days, the model is healthy. If breached >20 times, the model is failing.
- *Implementation*: Wire this directly into the `health.html` page as a "VaR Model Health" badge. High value, low effort (approx. 40 lines of code).

### Priority 3: Pre-Trade Liquidity Polish (`engine/risk/pre_trade.py`)
- **Status**: `MIN_ADV_RATIO = 0.01` is defined, but `check_adv_liquidity()` is never called.
- *Implementation*: Wire this existing placeholder into the execution logic using volume data from the `prices` table to establish a true "Days to Liquidate" limit.

### Priority 4: Marginal VaR (MVaR)
- **Concept**: Identifies which specific position contributes the most risk to the portfolio (factoring in correlation, not just weight).
- *Implementation*: Bolt this onto the Priority 1 Ensemble VaR engine, as the covariance matrix will already be computed.

### Priority 5: Correlation Stability Monitoring
- **Concept**: Flag when average pairwise correlation spikes by >20%, serving as a "diversification meltdown" early warning.
- *Implementation*: Feed off the existing `correlation_state.json` outputs generated by the research notebooks.

## 3. Secondary Polish & Refinements

### A. Tracking Error VaR (formerly "Relative VaR")
- Instead of calculating a naive ratio (Portfolio VaR / Benchmark VaR), compute the **Tracking Error VaR**: the VaR of the (Portfolio Return - Benchmark Return) series.

### B. Consensus Message (ML + GARCH)
- Combining ML signals and GARCH volatility into a single critical alert is conceptually sound, but the thresholds must be backtested first (e.g., "ML bearish AND GARCH tactical > 1.5x baseline"). 
- *Action*: Run historical analysis to ensure this rule doesn't fire constantly or never fire at all before hardcoding it.

---

## 4. Deprioritized (Do Not Build)
- **Phase 5 UI Re-layout**: The current risk tab UI is effective. Do not build new front-end elements (like Triple-VaR KPIs) until the backend Ensemble VaR engine is fully functioning.
- **Drift Correlation**: Tracking the correlation between portfolio drift and VaR increases is an interesting academic exercise but holds low actionable value for a manually executed fund.
